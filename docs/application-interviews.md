# Application interviews

Open an application and choose **Schedule interview**. Record the round, format (phone/video/onsite/other), start/end, interviewer, location, meeting URL, preparation and outcome. Times are entered in the profile timezone displayed when the editor opens; an open editor retains that timezone if the profile changes. Nonexistent daylight-saving times are rejected by the shared converter; ambiguous fall-back times use its existing resolution.

Scheduled interviews create a linked **LifeOS local** calendar event, also visible in daily planning. Rescheduling updates that same event. Completion retains the historical calendar entry. Cancellation removes the entry and retains the interview and every saved revision. Reactivating a cancelled interview creates a new event. The Calendar view links back to the application; direct calendar edits/deletes are blocked so they cannot bypass interview history. Meeting URLs and private preparation/outcome notes remain in the interview record, rather than being copied into calendar descriptions.

Application status and follow-up dates are independent. Recording an interview does not automatically change the pipeline or send invitations. This workflow does not create Google events or send recruiter messages. Local overlap checks reject scheduled interviews that overlap an existing local event (events without an end count as 30 minutes). Google/external conflicts are not checked here; concurrent generic calendar creation does not share the interview lock. Interview duration is limited to 24 hours. Multiple named rounds are allowed; past scheduled rounds remain scheduled until explicitly marked completed/cancelled.

Each creation has a stable request identifier and normalized payload fingerprint. Retries with the same identifier/data return the existing interview, including after later edits, without adding history/events. Reusing it for changed details returns 409. Edits require the loaded revision; stale edits return 409 and retain form text. Each successful edit appends a full snapshot to the history. Cancellation is the normal removal operation. Explicitly removing the application removes its interview history and all linked local events, while preserving the saved job.

Implementation: Application DTOs/service contract; Infrastructure owns validation, PostgreSQL transaction locking, calendar writes and revision history; controllers delegate. The unique user/request index prevents duplicate creations. Additive migration `20261016061122_ApplicationInterviews` creates the interview table with user/application cascades and no rewrite of existing data. Existing generic interview-like events are not converted automatically.

Validation: service tests with a mocked clock, WebApplicationFactory endpoint tests, frontend editor/timezone/DST/history/retry tests, and a disposable PostgreSQL test cover creation retries, conflicts, ownership, stale revisions, rescheduling, completed/cancelled history, calendar guards and separate application/follow-up state. General visual/mobile/accessibility QA remains open.

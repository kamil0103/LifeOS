# AI Coach mission review

**Suggest mission** creates a private suggestion, not an active mission. Review it, change task wording/category/priority/reason, reorder or remove tasks, add your own tasks, and edit the summary. **Apply mission** is the explicit step that creates today's mission and daily-plan actions. A generated suggestion survives reloads and can be discarded. Edits made inside the review editor are kept in memory and protected by the unsaved-change guard; those edits are not separately autosaved to the server.

Active unfinished missions can be edited with the same controls. Completed tasks stay in the mission and cannot be rewritten or marked incomplete through the editor. Up to ten reviewed tasks are supported; AI generation still suggests at most five. Applying/editing does not book time or modify existing calendar bookings. Existing bookings remain snapshots; manage their titles/times in Calendar. Daily planning continues to group actions by priority; the Coach mission list preserves the reviewed order.

Each task has a stable identifier. Older JSON records receive deterministic identifiers on read without a database rewrite. Their identifiers persist on the next edit/completion, keeping completion attached to a task after reordering. Old index-based completion requests are accepted only for untouched legacy JSON; once identifiers are persisted, an old positional request is rejected and asks the client to reload. Existing legacy scheduled action keys are not rewritten.

Edits include a loaded mission revision. Completion and editing use the same per-user PostgreSQL transaction lock; stale edits return 409 and leave the editor intact. Applying the same proposal again returns the already-created mission without overwriting later changes. Proposals from another local day cannot be applied. The current mission is never replaced by regeneration: edit today's mission instead. Historical and fully completed missions are not editable. Mark all complete retains the existing explicit whole-mission completion operation and marks every task complete.

Proposals use private `coach_mission_proposal` records in the existing Coach message table. They are excluded from chat history, saved memory and public insight lists. Warnings/encouragement appear as insights only after apply. No schema migration is required. Previously saved missions, chat and settings remain intact; existing AI-created missions are not retrospectively converted into drafts. Clients should reload after deployment to use task identifiers and the changed generate-mission response.

Validation includes AI-provider mocks, service/endpoint tests for draft-only generation, reviewed apply/replay, expiry/discard/ownership, stale revisions, legacy identifiers, completed-task preservation and stable completion after reordering. Frontend tests cover reviewed changes/order, failed-save retention, explicit apply, loaded revisions and recovering/discarding suggestions. A disposable PostgreSQL script seeds a synthetic proposal to test concurrency and lifecycle without making provider calls. General browser/mobile/accessibility QA remains open.
